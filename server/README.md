# DaBrawl persistent match server (deployment foundation)

This is a separate Node.js/WebSocket service intended for a persistent host (for example, a container service). It is deliberately separate from GitHub Pages and from the existing Supabase Edge Function prototype. It validates Supabase access tokens and owns room state, movement, basic projectile simulation, health, transformations, super-meter, knockouts, readiness, and match clocks in server memory. It limits rooms and per-socket message rates, validates input payloads, gives disconnected players a 10-second in-match reconnect grace period before forfeiting, transfers room ownership to the earliest remaining player if the former owner expires, and does not echo the access token as the negotiated WebSocket subprotocol.

## Important status

This service is **not yet connected to live DaBrawl matches**. The server now includes explicit baseline rules for Kuku, Shachi and Saiyan, including Shachi's slam and sequential Saiyan form progression with form-specific health, damage, range and projectile speed. Projectile collision uses a swept segment between ticks to avoid fast shots passing through targets, and registers the first valid opponent along that segment. Saiyan's charged Kame beam now uses server-owned hold timing (clients cannot submit a fake charge value), cooldown, line hits, form-specific damage scaling, and full-charge interior wall breaking. Mastered Ultra Instinct's max-form super now charges for 1.2 seconds, then fires a full-width 100-unit beam for 800 ms, deals repeated 7000/6 damage ticks to enemies in its line, and breaks interior walls along its path. Form-specific dodge/charge effects and exact client-side beam animation parity remain outstanding. Gadget use now has a server-owned single charge, cooldown enforcement, and cooldown values matching the browser's visible gadget timers (including Saiyan form variants); state snapshots expose charges and remaining cooldown. The server now builds the browser game's current tile layouts for Knockout/Duel (28×16 tiles) and Showdown (44×28 tiles), converts solid wall (`#`) and water (`~`) tiles into collision obstacles, and uses tested circular-player collision with axis sliding for walking and the simplified 70-unit gadget dash. Bushes (`b`) remain non-solid, matching the browser collision helper. This ports static movement geometry, but projectiles now stop at the first wall/water tile they cross, and super projectiles can destroy interior `#` walls. Destroyed wall coordinates are included in state snapshots and wall-break events. Exact browser map collision edge cases and all form-specific ability effects still need parity work. The server still uses a simplified 70-unit dash for accepted gadget activations, so form-specific gadget effects are not gameplay-parity complete. Player movement and gadget dashes clamp the entire player collision radius inside arena bounds. Shared boundary helpers have regression tests and are included in the production Docker image. Remaining work includes full bot AI, additional form-specific abilities, and a real two-player hosted test. Do not switch production matchmaking to it until the client protocol and all brawler rules are ported and verified. The existing Supabase Realtime path remains untouched.

## Host

Deploy this directory as a Node 20+ container. Set the Dockerfile path to `server/Dockerfile` and the build context to the repository root (equivalent to `docker build -f server/Dockerfile .`). Configure `SUPABASE_URL` and `SUPABASE_ANON_KEY` from the DaBrawl Supabase project. Start command: `npm start`; liveness endpoint: `/health`; readiness endpoint: `/ready` (returns HTTP 503 until `SUPABASE_URL` and `SUPABASE_ANON_KEY` are configured); WebSocket path: `/match?room=ROOM_CODE`. Do not add a service-role key.

## Local checks

Run `npm run check` and `npm test` from this directory. Unit tests cover message parsing, room-code validation, movement-axis validation, supported modes, player-name sanitization, active-match phase guards, team assignment, disconnect grace-window and room-retention boundaries, browser adapter mapping, Saiyan form stats and bounded progression, gadget charge/cooldown boundaries, and deterministic projectile movement, first-contact collision filtering, swept collision, range and world bounds. GitHub Actions also builds the production Docker image so missing files or invalid container build steps are caught before deployment.

## Isolated browser test client

Open [`test-client.html`](./test-client.html) in a browser, enter a hosted WebSocket URL ending in `/match`, a test room code, and a Supabase **user access token**. Open the page in a second tab with a different authenticated user to exercise two-player join/ready/movement/action snapshots. The page keeps the token only in JavaScript memory and does not write it to browser storage. Never enter a service-role key. The test client is only a protocol/arena inspector, not the production game UI; it cannot connect until the server is hosted and configured. Use `wss://` for a real hosted environment.

## Wire protocol

Authenticate with WebSocket subprotocols `jwt-<Supabase access token>` and `dabrawl-v1`. Send `join` with a player name, brawler id, mode, and readiness state after connection. A match starts only after at least two players have joined and every player is ready. Knockout teams split the ordered roster into two balanced sides; duel alternates sides; showdown treats each player as a separate team. Then send sequenced `input` messages (`x`, `y`, `aim`) and action messages (`fire`, `super`, `transform`, `gadget`). Combat actions are ignored outside the active `playing` phase, and projectiles are cleared outside that phase. The server sends complete `state` snapshots, `ack`, and `event` messages. If the process restarts, clients receive a WebSocket close (code 1012); in-memory rooms are lost, so durable room recovery is still a separate task.

## Live-client integration boundary

See [CLIENT-INTEGRATION.md](./CLIENT-INTEGRATION.md) for the field/event mapping and safe rollout checklist.

The current browser game still uses Supabase Realtime broadcasts (`match-state`, `player-state`, `player-action`) and a game-specific state shape (`x`, `y`, `a`, `hp`, `mh`, `sc`, `am`, and other combat fields). That wire format is not compatible with this service protocol yet. Integration must use an explicit adapter, move authority for damage and abilities to the server, and stop the browser host from simulating the same match twice. Do not simply redirect the existing broadcasts to this socket: doing so would create mismatched snapshots and desynchronized combat.


Charge interruption is handled server-side as well: disconnect forfeits, projectile knockouts, beam knockouts, and room cleanup cancel any unfinished Saiyan Kame charge so dead or removed players cannot retain a stale charging state.
