# DaBrawl persistent match server (deployment foundation)

This is a separate Node.js/WebSocket service intended for a persistent host (for example, a container service). It is deliberately separate from GitHub Pages and from the existing Supabase Edge Function prototype. It validates Supabase access tokens and owns room state, movement, basic projectile simulation, health, transformations, super-meter, knockouts, readiness, and match clocks in server memory. It limits rooms and per-socket message rates, validates input payloads, gives disconnected players a 10-second in-match reconnect grace period before forfeiting, transfers room ownership to the earliest remaining player if the former owner expires, and does not echo the access token as the negotiated WebSocket subprotocol.

## Important status

This service is **not yet connected to live DaBrawl matches**. The existing Supabase Realtime path remains untouched; do not switch production matchmaking to this server until the client protocol, all brawler rules, and a real two-player hosted test have been verified.

The server has explicit baseline rules for Kuku, Shachi, Saiyan, Degeš, and Ramu. Saiyan has server-owned transformation progression and charge timing. Degeš’s lobbed beer attacks travel over walls; his gadget starts a stationary, vulnerable two-second smoke channel that fully heals him at completion, with a 15-second cooldown after the channel. Ramu is labeled Mythic / Transformer in the browser, with the description “Transform into fire or ice.” His Ice attack spends one ammo on three 1000-damage orbs launched 170 ms apart, with a 750 ms per-volley cooldown; eight hits freeze an opponent for two seconds. His Super alternates Ice and Fire. Fire mode drains energy continuously, reaches its 285-unit range in about 400 ms, then deals 1000 damage every 350 ms (15 hits / 15000 direct damage from a full bar) and charges Super modestly faster; the bar lasts about 5.6 seconds, locks for 200 ms after empty, and recharges slowly only after release. Sustained Fire heats normal walls to neon orange and breaks them after five seconds; released heat cools at half the build rate. Twelve Ice-ball impacts make a wall cyan and indestructible until five seconds of sustained Fire melts it. His Ice gadget immobilizes him inside the shield; his Fire gadget launches him out of view, then allows five seconds of wall-crossing movement before a 2000-damage, burning landing that knocks enemies back and breaks nearby normal walls; its 20-second cooldown starts on landing. A landing over water is resolved to nearby dry ground. The browser renders Fire as turbulent flame ribbons rather than a laser and leaves fading flame trails on dive launch and landing.

Projectile collision uses swept segments and selects the first valid opponent. Degeš bottles intentionally arc over obstacles. Other projectiles stop at the first wall/water tile; Ramu Ice balls heat up wall-frost state and all wall-breaking abilities respect indestructible Ice walls. State snapshots include destroyed wall coordinates, wall heat/ice state, and Ramu’s mode/status timers. The server builds the browser’s current Knockout/Duel (28×16) and Showdown (44×28) tile layouts, with circular-player collision, axis sliding, and clamped arena boundaries. Bushes remain non-solid. Exact browser collision and visual/animation parity still need validation.

The server includes room-owner-requested bots. Bots select nearby enemies, strafe, retreat or close based on range, dodge incoming projectiles, avoid gas, and use server-authoritative fire, super, gadget, and Saiyan transformation rules. Movement scores 16 short collision-aware directions; this is local reactive navigation, not full route planning, so complex layouts can still trap a bot. Generic 70-unit gadget dashes remain only for Kuku, Shachi, and Saiyan; Degeš and Ramu use their custom server effects. The isolated test client and adapter are development tools, not the production game UI.
## Host

Deploy this directory as a Node 20+ container. Set the Dockerfile path to `server/Dockerfile` and the build context to the repository root (equivalent to `docker build -f server/Dockerfile .`). Configure `SUPABASE_URL` and `SUPABASE_ANON_KEY` from the DaBrawl Supabase project. Start command: `npm start`; liveness endpoint: `/health`; readiness endpoint: `/ready` (returns HTTP 503 until `SUPABASE_URL` and `SUPABASE_ANON_KEY` are configured); WebSocket path: `/match?room=ROOM_CODE`. Do not add a service-role key.

## Local checks

Run `npm run check` and `npm test` from this directory. Unit tests cover message parsing, room-code validation, movement-axis validation, supported modes, player-name sanitization, active-match phase guards, team assignment, disconnect grace-window and room-retention boundaries, browser adapter mapping, Saiyan progression, Degeš smoke-heal rules, Ramu Ice volleys, continuous Fire energy and status timers, gadget cooldowns, and deterministic projectile movement/collision. GitHub Actions also builds the production Docker image so missing files or invalid container build steps are caught before deployment.

## Isolated browser test client

Open [`test-client.html`](./test-client.html) in a browser, enter a hosted WebSocket URL ending in `/match`, a test room code, and a Supabase **user access token**. Open the page in a second tab with a different authenticated user to exercise two-player join/ready/movement/action snapshots. The page keeps the token only in JavaScript memory and does not write it to browser storage. Never enter a service-role key. The test client is only a protocol/arena inspector, not the production game UI; it cannot connect until the server is hosted and configured. Use `wss://` for a real hosted environment.

## Wire protocol

Authenticate with WebSocket subprotocols `jwt-<Supabase access token>` and `dabrawl-v1`. Send `join` with a player name, brawler id, mode, and readiness state after connection. A match starts only after at least two players have joined and every player is ready. Knockout teams split the ordered roster into two balanced sides; duel alternates sides; showdown treats each player as a separate team. Then send sequenced `input` messages (`x`, `y`, `aim`) and action messages (`fire`, `super`, `transform`, `gadget`). The room owner may send action `add-bot` while the room is waiting; each added bot is server-controlled and ready by default, but the human owner still needs to ready up. Combat actions are ignored outside the active `playing` phase, and projectiles are cleared outside that phase. The server sends complete `state` snapshots, `ack`, and `event` messages. If the process restarts, clients receive a WebSocket close (code 1012); in-memory rooms are lost, so durable room recovery is still a separate task.

## Live-client integration boundary

See [CLIENT-INTEGRATION.md](./CLIENT-INTEGRATION.md) for the field/event mapping and safe rollout checklist.

The current browser game still uses Supabase Realtime broadcasts (`match-state`, `player-state`, `player-action`) and a game-specific state shape (`x`, `y`, `a`, `hp`, `mh`, `sc`, `am`, and other combat fields). That wire format is not compatible with this service protocol yet. Integration must use an explicit adapter, move authority for damage and abilities to the server, and stop the browser host from simulating the same match twice. Do not simply redirect the existing broadcasts to this socket: doing so would create mismatched snapshots and desynchronized combat.


Charge interruption is handled server-side as well: disconnect forfeits, projectile knockouts, beam knockouts, and room cleanup cancel any unfinished Saiyan Kame charge so dead or removed players cannot retain a stale charging state.
